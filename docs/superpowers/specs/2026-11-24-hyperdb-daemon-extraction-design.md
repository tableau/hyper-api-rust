# Extract the shared-`hyperd` daemon into a `hyperdb-daemon` crate — design

**Status:** Draft from a read-only spike, 2026-11-24, revised the same day to
move the shared engine to TCP with a password (D5, D6). Not scheduled.
**Plan:** [`../plans/2026-11-24-hyperdb-daemon-extraction.md`](../plans/2026-11-24-hyperdb-daemon-extraction.md)

## Summary

`hyperdb-mcp` contains a single-instance daemon that keeps one `hyperd` warm and
shares it across MCP clients: discovery file, single-instance lock, health and
control channel, supervision with crash restart, and idle shutdown. That
machinery is useful to ordinary Hyper API users — test suites, CLIs invoked in
a loop, warm worker pools — but today it can only be reached from the MCP.

This design splits the work into four phases, each of which can stop there:

| Phase | What | Public API? | Rough size |
|---|---|---|---|
| **0** | Measure `hyperd` startup cost and idle RSS | No | ~0.5 day |
| **S** | Control-command token; engine password on TCP; strict-SCRAM client | No | ~3–4 days |
| **A** | Move `hyperdb-mcp/src/daemon/` into a new `hyperdb-daemon` crate, positioned as internal | No | ~2–3 days |
| **B** | User-facing `acquire()` API: cohorts, leases, protocol version, a launcher | Yes | ~1.5–2 weeks |

Sizes are agent time including review and CI iterations, not calendar time.
Phase B also depends on the open issue #242, which is not sized here.

## What exists today

`hyperdb-mcp/src/daemon/` is nine files and about 7,400 lines, including inline
unit tests:

| Module | Role |
|---|---|
| `spawn` | Find or start the daemon (`ensure_daemon`), version takeover |
| `discovery` | State directory, `daemon.json` read/write, trusted-endpoint checks |
| `lock` | Single-instance `daemon.lock` |
| `control` | Health channel transport: Unix socket or named pipe, peer checks |
| `health` | Command loop: `PING`, `HEARTBEAT`, `STOP`, `STATUS`, `REPORT_HYPERD_ERROR` |
| `run` | Daemon main loop, `HyperProcess` supervision, restart limiter, idle timeout |
| `state_perms` | Owner-only directory and file permissions |
| `legacy` | Compatibility with daemon records written by pre-1.0 daemons |
| `mod` | Constants (`DEFAULT_IDLE_TIMEOUT_SECS`, `ENV_IDLE_TIMEOUT`) |

The daemon already talks to its engine over IPC (#304): `run::build_params` sets
`TransportMode::Ipc` and points `domain_socket_directory` at an owner-only
directory under the state dir. On Windows the named pipe uses `hyperd`'s default
owner-only DACL.

## Spike findings

### 1. Coupling into the rest of `hyperdb-mcp` is small

References from `daemon/` to non-daemon modules:

| Reference | Uses | Where |
|---|---|---|
| `crate::diagnostics::{ReportedPath, PathEncoding}` | 14 | `discovery.rs` |
| `crate::version::{MCP_VERSION, mcp_version_string}` | 4 | `spawn.rs`, `health.rs`, `discovery.rs` |
| `crate::paths::persistent_home_dir` | 1 | a doc comment in `discovery.rs` only |

External crates used: `std`, `tokio`, `serde`, `serde_json`, `tracing`,
`tempfile`, `chrono`, `hyperdb_api`, and `libc` / `windows-sys` per platform.
None are MCP-specific (`rmcp`, `arrow`, `plotters` and the rest are not used).

Inbound users: `main.rs`, `engine.rs`, `server.rs`, `diagnostics.rs`, and
integration tests through `hyperdb_mcp::daemon::…`, for example
`spawn::client_should_take_over`, `run::STARTUP_WAIT` and
`run::DaemonConfig::from_args`.

### 2. The real blocker is how the daemon process is launched

`spawn.rs` starts the daemon by re-running the current executable with a
`daemon` argument (`std::env::current_exe()` plus `.arg("daemon")`). So the
daemon process *is* the `hyperdb-mcp` binary. A Hyper API user's program has no
`daemon` subcommand, and a `cargo test` binary is generated by libtest and
cannot take one at all. That is the single largest design question for
Phase B; see [D8](#d8--launcher-for-library-users-open).

Phase A does not need to solve it: the MCP keeps launching itself.

### 3. Mechanical traps for the move

- **Hard-coded test paths.** `discovery.rs` re-execs its own unit-test binary
  with a filter string naming the test path, for example
  `"daemon::discovery::tests::raw_discovery_rejects_fifo_without_blocking"`.
  After the move the path loses its `daemon::` prefix. A stale filter matches
  zero tests, so the child runs nothing and the parent can pass for the wrong
  reason. Every such string must be updated and the child's test count checked.
- **`pub(crate)` items** that `hyperdb-mcp` uses (for example
  `DaemonRecord::executable_path` and `DaemonRecord::mcp_version`) stop being
  reachable across the crate boundary and must become `pub`.
- **Product identity.** The PONG token, `daemon.json`'s `mcp_version`, and the
  takeover rule all read `MCP_VERSION`. These need a seam, not a global.

### 4. Correction: there is no pre-1.0 deadline for Phase A

An earlier exploration argued the extraction had to happen before 1.0 because a
later move would be breaking. That no longer holds. `hyperdb-mcp/src/lib.rs`
declares the library target explicitly *not* a public API: every module is
`#[doc(hidden)]`, and only the MCP tool surface is semver-governed. Moving
`daemon` out later is therefore not a breaking change for anyone.

What *does* matter for 1.0 is how the new crate is positioned. If
`hyperdb-daemon` ships at the lockstep `1.0.0` with a documented API, that API
is frozen at 1.0. Phase A avoids this by positioning the crate as internal,
following the `hyperdb-api-core` precedent, until Phase B designs the real
surface.

## Goals

- Phase A: the daemon lives in its own crate; `hyperdb-mcp` behaviour,
  on-disk formats, the control protocol, and the MCP tool surface are unchanged.
- Phase B: a Hyper API user can share one warm `hyperd` across processes of the
  same application, opt-in, with a typed error or an observable fallback when
  sharing is unavailable.

## Non-goals

- Sharing across unrelated applications or trust domains.
- A network-reachable daemon. The engine listens on loopback only
  (`127.0.0.1`). A remote engine is a plausible later extension, because D6's
  TCP-plus-SCRAM model does not tie authentication to the local machine. It
  would need its own design for TLS, credential provisioning to remote
  clients, and a remote control channel; nothing here should preclude it.
- Changing `HyperProcess`'s default transport. It stays TCP.
- Moving MCP policy into the crate: attachment replay, the persistent and
  ephemeral database model, the catalog, the KV store, watched directories,
  the doctor, and the MCP's version-takeover UX all stay in `hyperdb-mcp`.

## Decisions

### D1 — Phase A ships an internal crate

`hyperdb-daemon` joins the workspace, is lockstep-versioned like every other
crate, and is published (Cargo requires it, since `hyperdb-mcp` depends on it).
Its README and crate docs state that it is not yet a public API, mirroring
`hyperdb-api-core/README.md`. Phase B makes it public additively, in a minor
release.

- **Rejected — independent `0.x` versioning.** The release model is a single
  release-please package (`"."`) with lockstep pins. An independently
  versioned crate would need a second package and its own tag stream.

### D2 — The MCP keeps its binary and subcommand

`hyperdb-mcp daemon` stays the MCP's daemon entry point and calls
`hyperdb_daemon::run::run_daemon`. `hyperdb_mcp::daemon` becomes
`pub use hyperdb_daemon as daemon;`, so existing `crate::daemon::…` and
`hyperdb_mcp::daemon::…` paths keep compiling with no churn in `main.rs`,
`engine.rs`, `server.rs`, `diagnostics.rs`, or the integration tests.

### D3 — A product-identity seam replaces `MCP_VERSION`

Introduce a small value type, provisionally:

```rust
#[derive(Clone, Debug)]
pub struct DaemonIdentity {
    /// Token in the PONG reply and the discovery record, e.g. "hyperdb-mcp".
    pub product: &'static str,
    /// Semver used by the takeover rule.
    pub version: &'static str,
    /// Human-readable version for STATUS and daemon.json, e.g. with git hash.
    pub version_string: String,
}
```

The MCP constructs it from `crate::version` and passes it into `DaemonConfig`
and `ensure_daemon`. Wire output is byte-for-byte unchanged: same PONG token,
same `mcp_version` JSON key. Renaming the key is a Phase B protocol change, not
a refactor.

Do this refactor *inside* `hyperdb-mcp` first, so the move itself is purely
mechanical.

### D4 — `ReportedPath` and `PathEncoding` move with the daemon

They are bounded, display-safe path types. Move them to
`hyperdb_daemon::report_path` (name provisional) and re-export them from
`hyperdb_mcp::diagnostics`, so the doctor's code is untouched.

### D5 — The shared engine listens on TCP loopback, with a password

The shared engine listens on `127.0.0.1` and requires a per-daemon password
(D6). This keeps TCP's throughput, which IPC does not match for bulk work.
Measurements behind the comment in `hyperdb-api/src/process.rs` and
`docs/BENCHMARK_GUIDE.md`:

| Workload | IPC vs TCP loopback |
|---|---|
| Connect | about 30% faster (macOS, Unix socket) |
| Small round-trip | about 19% faster (macOS) |
| Streamed reads past about 10k rows | up to 62% slower (macOS) |
| Windows named pipe, single-connection insert | 34–41% slower |
| Windows named pipe, async full scan | 76% slower |

The password gives the TCP listener the same boundary the IPC transports get
from file permissions: connecting requires reading an owner-only file.

**TCP over the PostgreSQL protocol is the only transport.** New daemons never
create an IPC or gRPC listener:

- **No IPC option.** A second transport means a second permission model to
  build, test and document. Its connect-latency gain matters little once
  connections are pooled. Clients still connect to an *older* daemon whose
  record names a socket or pipe, for the upgrade transition only.
- **No gRPC.** `hyperd`'s gRPC service accepts only trusted users. Making
  gRPC work would need a password-less user, which any local process could
  use over TCP, undoing D6. Probed on 2026-11-24 with the D6 config: a gRPC
  query with no user was refused ("access denied"), and one naming the engine
  user was refused ("gRPC connections only support trusted authentication").
  Nothing is
  lost: the MCP does not use local gRPC (the gRPC kind in `attach.rs` is a
  planned remote Data 360 attach with its own authentication), and Arrow reads
  work over PostgreSQL TCP through `ArrowReader`. Callers who want a local
  gRPC engine keep private `HyperProcess` with `ListenMode::Grpc` or
  `ListenMode::Both`.

Private mode (`HyperProcess`) is unchanged by this design. It could adopt the
same mechanism later as separate work.

### D6 — Engine credential: a generated password, delivered by config file

**Decided (maintainer, 2026-11-24):** the config-file route below, with the
environment variable kept as a documented fallback. Each daemon
start generates a random password and gives the engine only its SCRAM-SHA-256
verifier. Verified against the pinned `hyperd` (0.0.26479) on 2026-11-24, both
directly and through `HyperProcess` with no `hyperdb-api` change.

**Primary route: a `hyperd` settings file.**

- The daemon writes `<state-dir>/engine/hyperd-auth.json`, created owner-only
  (mode `0600` at creation, not `chmod` afterwards; on Windows, the existing
  owner-only DACL helpers), containing:

  ```json
  {"authorized_users": [{"name": "tableau_internal_user", "superuser": true,
    "authentication": {"method": "scram_sha256",
      "encrypted_password": "SCRAM-SHA-256$4096:<salt>$<StoredKey>:<ServerKey>"}}]}
  ```

- It starts `hyperd` with the `config` and `strict_settings_mode` parameters
  (`--config=<file>` and `--strict-settings-mode` in `hyperd --help`).
- The password itself goes only into `daemon.json`, for clients.
- The daemon computes the verifier itself, in the standard PostgreSQL format
  (PBKDF2-HMAC-SHA256, then `HMAC("Client Key")` hashed and
  `HMAC("Server Key")`), reusing the primitives in
  `hyperdb-api-core/src/client/auth.rs`. `hyperd scram-sha256-hash` cannot be
  used: it reads the password from the terminal and hangs when its input is
  piped.

Properties confirmed by the probe:

- The password appears neither in `hyperd`'s arguments nor in its environment
  (`ps eww`).
- `hyperd` never reaches its password prompt when `authorized_users` is set.
- The `--no-password` that `HyperProcess` adds by default is ignored when
  `authorized_users` is set; no password, a wrong password and the right one
  give rejected, rejected and connected.

**Strict settings mode is mandatory.** Without it, `hyperd` treats an unknown
setting name as a warning and starts anyway, and the `--no-password` default
from `HyperProcess` would then apply. With `--strict-settings-mode` an
unrecognised setting fails startup (exit 1, "Critical setting errors
encountered"), so the engine either starts with the configured user or not at
all.

**Startup self-check.** Before the daemon writes `daemon.json`, it connects to
the engine with no password and requires a rejection. If the engine accepts
the connection, the daemon stops `hyperd` and fails startup. This catches any
other way the engine could come up unauthenticated, including a future change
in how `--no-password` and `authorized_users` interact.

**Fallback route: the `HYPER_INITIAL_USER_PASSWORD` environment variable.**
`authorized_users` is not listed in `hyperd --help`, but it appears in
publicly visible Hyper configurations, which is why the maintainer accepted
it. If a `hyperd` bump breaks the pin-bump test, or the Hyper team advises
against it, switch to the environment variable, which is also absent from
`--help`. Consequences:

- The password is in `hyperd`'s initial environment and visible to the same
  user through `ps eww`. That is no new exposure, because the same user can
  read `daemon.json`.
- `--no-password` must be omitted, and the variable must always be set:
  without either, `hyperd` prompts on the terminal. A test must show that a
  missing variable fails startup rather than hangs.
- `HyperProcess` needs two additions in `hyperdb-api`: a way to suppress the
  default `--no-password`, and a way to set the child's environment. Both are
  public API changes.

Only the daemon's parameter builder (`run::build_params`) and the new
password module change between the two routes.

**The client requires SCRAM.** A password on the server is only half the
mechanism; the client must also insist on it. Connections to a shared engine
use a new strict mode in `hyperdb-api-core/src/client/connection.rs` (and its
async twin), comparable to libpq's `require_auth=scram-sha-256`, while the
default mode keeps today's behaviour for other servers. In strict mode the
connection succeeds only if the server ran
SCRAM-SHA-256 and its final message verified (`scram_verify_server`). Every
other authentication request, and an `AuthenticationOk` before a verified
SASL final, is an error before any query is sent.

**No gRPC listener** (D5): `hyperd`'s gRPC service cannot authenticate a SCRAM
user, so the daemon never enables it.

### D7 — A capability token gates state-changing control commands

Generate a random token per daemon start, store it in the owner-only
`daemon.json`, and require it on `STOP` and `REPORT_HYPERD_ERROR`. `PING`,
`STATUS` and `HEARTBEAT` stay open. This is defence in depth: today these
commands are only reachable by the owning user, so this is hardening, not a
fix. Phase S, and independent of the extraction.

Compatibility: a pre-token client talking to a token-requiring daemon must be
handled deliberately. The plan specifies the behaviour and a test for it.

### D7a — Upgrading from pre-1.0 clients and daemons

Nobody has to uninstall an older `hyperdb-mcp` before using a newer one. The
daemon is per user (one per state directory), and the existing version rule
only ever replaces an *older* daemon: a newer client sends it `STOP` and starts
its own; an older or equal client reuses whatever is running. Phase A changes
none of this, because the binary, tool surface, record format and control
protocol stay as they are. Only Phase S (D6, D7) can break a mixed install:

| Client | Daemon | Result |
| --- | --- | --- |
| newer | older | The client takes the daemon over, or keeps using it: a record with no password or token behaves as today. |
| older | newer | The client cannot authenticate to the shared engine and gets `ERR unauthorized` on `STOP`. It cannot take over a newer daemon, so it fails for as long as that daemon runs. |

The second row is the case to handle. It arises when an old client stays
running next to a newer one (for example, a version pinned in a second editor).
**Decision:** from 1.0, pre-1.0 clients are unsupported against a 1.0 daemon.
There is no compatibility layer, as with the earlier move of the health channel
off TCP. What the design adds is clarity, not compatibility:

- The first release carrying Phase S documents the rule in the `hyperdb-mcp`
  changelog and release notes: upgrade every client together.
- The daemon reports a rejected client in `STATUS` and its log, with a message
  that names the upgrade, so a failure is diagnosable from the daemon side.
- An already-shipped client cannot be changed, so its own error text is outside
  the design. Phase S includes a test that records what an old client sees, and
  the changelog quotes it.

### D8 — Launcher for library users (open)

How does a library caller start a daemon when the host binary has no `daemon`
subcommand?

| Option | How | Works for `cargo test`? | Cost |
|---|---|---|---|
| **L1** host hook | Host calls `hyperdb_daemon::run_if_requested()` first thing in `main`; spawn re-execs `current_exe` with an env var | **No** — libtest owns `main` | None to ship |
| **L2** standalone binary | Ship a `hyperdb-daemon` binary; locate it via `HYPERDB_DAEMON_PATH`, beside `hyperd`, or on `PATH` | Yes | A distribution artifact (`cargo install`, or a release download) |
| **L3** no supervisor | First client spawns a detached `hyperd`; no daemon process | Yes | Loses restart, idle shutdown and leases |

**Recommended: L2**, with L1 as an optional extra for applications that prefer
not to ship a second binary. The primary motivating workload — test suites —
rules out L1 alone.

### D9 — Phase B API: adopt the earlier exploration's shape

The offline design exploration proposed an API worth keeping. In brief:

- **Cohorts.** A daemon is keyed by a caller-supplied cohort name, with state
  under `~/.hyperdb/daemons/<cohort-hash>/`. The MCP stays on `~/.hyperdb` for
  compatibility. No machine-wide default for libraries.
- **Three explicit intents.** `Acquisition::{Private, Shared, SharedOrPrivate}`.
  `Private` is the default and is today's `HyperProcess`. `Shared` fails with a
  typed error. `SharedOrPrivate` has a hard `fallback_deadline` and reports why
  it fell back, logged at `warn`.
- **Leases.** Clients register on acquire and release on drop; the idle timer
  runs only at zero leases; heartbeats expire leases of dead clients. Idle
  timeout is **on** by default for library daemons, so a test run leaves no
  resident service behind.
- **Libraries never take over.** A library never sends `STOP` to an older
  daemon. An incompatible daemon is treated as absent and a separate cohort
  daemon is started. Takeover stays an MCP and operator action.
- **Protocol version.** An integer in `daemon.json` and the `PING` reply,
  versioned independently of the crate; clients support N and N-1.
- **Surface.** `acquire(how, &Options) -> Result<Engine>` and `acquire_async`,
  with `Engine::endpoint()` plus the engine credentials (D6) usable by every
  existing `hyperdb-api` connect API and by `PoolConfig`, with strict SCRAM
  switched on. `Options` is `#[non_exhaustive]`. Dropping a
  `SharedEngine` releases its lease and does **not** stop `hyperd`.

Phase B gets its own spec revision before work starts; this section only fixes
the direction.

## Open decisions for the maintainer

1. **Go / no-go on Phase B**, after Phase 0's numbers. Suggested bar: if a
   release-mode `HyperProcess::new()` to first query is well under a second on
   macOS and Linux, the sharing benefit is small for most users and Phase A is
   the place to stop.
2. **D8:** L2 alone, or L2 plus L1.
3. **Timing of Phase A:** any time; there is no 1.0 deadline (finding 4). It
   can wait until after the Linux ARM work lands, which touches the same
   release plumbing.

## Risks

- **Stale test filters** (finding 3) passing vacuously. Mitigated by asserting
  the child's test count in the plan's gate.
- **Windows-only code** in `control.rs` and `state_perms.rs` that only CI
  compiles. Mitigated by local Windows-target clippy before pushing.
- **Release plumbing drift.** A new crate must be added to the publish order,
  lockstep pins and every crate list. Missing one fails the release, not CI.
- **Internal `hyperd` setting** (D6). `authorized_users` could change format
  or be renamed in a `hyperd` release. Mitigated by strict settings mode (an
  unknown setting fails startup), the startup self-check, and an integration
  test that the `update-hyperd-release` procedure runs on every pin bump. The
  environment-variable route is the planned fallback.
- **Phase B security review.** The control-protocol changes (token, leases,
  protocol version) should get an independent security review before release.
